# Phase 1 architecture

## Persistence and authorization

SQLite with WAL runs on the existing server using `better-sqlite3`. This avoids another database service for an initial single-server pilot. Transactions serialize membership counts, schedule revisions, entity writes, history and retry receipts. The web server and the worker are separate processes on the same file, so every transaction that may write starts with `BEGIN IMMEDIATE` (`db.transaction(fn).immediate()`): it waits up to `busy_timeout` (5 s) for the other process's write lock, instead of failing at once with `SQLITE_BUSY` when a read inside a deferred transaction has to become a write. Read-only snapshots (chat inbox and thread polls) stay deferred. So does `verifyByDomain`'s small write in `src/server/community.ts`, which reads nothing inside its transaction: its first statement is the `INSERT`, so it takes the write lock at once and waits on `busy_timeout` like an immediate one (a deferred transaction that may write must never read before its first write). A calendar refresh that still finds the database busy releases its lease and records no feed error (`isBusy`). The schema is initialized idempotently and each migration records its version in `schema_migrations`; future schema changes must add explicit migrations. `openDatabase` runs every migration step inside one `BEGIN IMMEDIATE` transaction, because the web server and the worker restart together after a deploy and both open the file: the second opener waits for the first and then finds each step already applied, instead of racing a check-then-`ALTER` ("duplicate column name") or failing with `SQLITE_BUSY_SNAPSHOT`. A failed migration rolls back as a whole and its handle is closed, so the next `getDb()` call simply tries again. Migration 8 adds indexes for the `audit_log` lookups (per-account rate limits by actor, action and time; report history by action) and for the cascade from `push_subscriptions` to `notification_deliveries`. Migration 9 indexes `notification_deliveries` by `reminder_at` and by `(entity_id, updated_at)` for the worker's per-minute prunes. Migration 10 indexes `friendships` by `(requester_id, status)` for the pending friend-request limit and `push_subscriptions` by `(owner_id, created_at)` for the per-recipient push lookups. Migrations 11 and 13 repair out-of-range task dates (see phase 2 below), and migration 12 stores each proposal's last tally (see phase 3 below). Use local storage with reliable locks. The repository happens to live under `/srv/NAS`; put the database on local disk or a local Docker volume, not an NFS/SMB mount.

Google OAuth is the only authentication provider. A verified Google email is required. A refused or failed sign-in returns to `/` with NextAuth's `?error=` code (`pages` in `src/server/auth.ts`), and the landing page explains it in a callout (`signInErrorMessage`): an unverified Google email, a cancelled or failed Google round trip, or a server setup fault. When NextAuth also passes the failed attempt's `callbackUrl` (for example `/admin`), the landing page keeps it if it is on this origin (`signInReturnPath`), so retrying from there returns the owner to the admin console. Google subject identifies the account; both names must be entered before onboarding mutations. JWT sessions are encrypted and expire after 30 days. Owner privileges are checked against `OWNER_EMAIL` server-side on every admin operation. School verification is separate (see phase 3 below); Google email verification does not by itself mark a student school-verified.

All tRPC workspace, school and personal operations require a session. The service scopes records and receipts by the authenticated owner. A supplied user ID cannot change this. Every student mutation is also bound to the account the tab composed it under: its input carries `accountId`, and the router answers `UNAUTHORIZED` when that is not the cookie's account (the `accountScoped` middleware, or the same check written inline in `sync` and the `notifications` mutations). This covers sync, reminders, calendars, the class directory, community, proposals, scans and chat, and the profile and school mutations (`profile.save`, `school.create`, `join`, `update`, `acknowledge`, `requestCorrection` and `feedback`), so a form left open as one account can never rename, move or file requests for another account after a switch in another tab. A request to an `accountScoped` procedure that has no `accountId` field at all comes from a tab still running a bundle built before the procedure was account-scoped, so the router answers `PRECONDITION_FAILED` with "Quasar has been updated. Reload the page, or close and reopen the app, to continue." (`OUTDATED_CLIENT_MESSAGE`, from the `requiresField` middleware) instead of the generic validation message. A present but wrong `accountId` is still `BAD_REQUEST` or `UNAUTHORIZED`. The owner's school and inbox mutations (`admin.update`, `resolveRequest`, `decideVerification`, `resolveReport`, `removeMember` and `decideProposal`) carry no `accountId` and rely on the `OWNER_EMAIL` check alone, so after a switch to another account a stale owner action fails with `FORBIDDEN` rather than running as that account; the four chat admin mutations and `global.edit` use `adminScoped`, which adds the account check (see phase 4). JSON POSTs additionally require a same-origin `Origin`. No authenticated API responses enter the service-worker cache. The `/` page is rendered per request from the session cookie (`src/app/page.tsx`): a signed-out visitor gets the landing page and a signed-in student gets their workspace inlined, so the first paint is the real screen with no API round trip in front of it (the client then opens its device store, which adds that device's waiting changes, and syncs in the background). The response is not cacheable by browsers, and the service worker caches only its own credentials-omitted fetch of the page, so the offline shell stays the public, signed-out one; opened offline, that shell still loads the device's saved workspace. `/admin` renders its verdict (sign in, owner access required, or the support tools) the same way. Local account data intentionally remains readable while offline until explicit signout; do not use a shared browser profile for confidential offline data. Error messages students see are written for them: services throw a `TRPCError` with a specific code and a fixed message, the router's `errorFormatter` turns zod's built-in wording into a generic "check the fields" sentence, and any unexpected failure (a plain `Error` such as a `SqliteError`, which tRPC wraps as `INTERNAL_SERVER_ERROR` with the raw text) is shown only as "Something went wrong. Please try again." (`SERVER_ERROR_MESSAGE`), so table and column names never reach the UI.

Only members may edit their current school's unlocked default. The tenth distinct member permanently sets `member_locked`, including if membership drops later. Support locks are separate and owner controlled. Owners can correct either lock. Every default revision is retained. Unapproved defaults require explicit selection. Member edits revoke approval; an owner can approve and lock. Creation does not automatically join or select a schedule. The support inbox accepts schedule evidence/links as text; formal evidence criteria remain a pilot policy decision.

## Scheduling rules

`src/domain/schedule.ts` is shared by client, server validation and tests. `exampleSchedule` provides a ten-day example; no cycle length is hardcoded.

- Periods have stable IDs and kind `class`, `lunch`, or `other`; a student's class assignment follows that period through the rotation.
- Cycle days have stable IDs and ordered, non-overlapping slots. The same period may appear in more than one slot, supporting a class split around lunch. Lunch waves can be separate lunch period IDs.
- The anchor names the cycle day on a calendar date. Advancement occurs after that date. Attendance weekdays and advancement weekdays are independently configurable (ISO weekdays Monday=1 through Sunday=7).
- Closures explicitly pause or advance the cycle. Replacement dates provide special slots and an advancement decision. Reset exceptions select the cycle day for that date and following dates, supporting term transitions, and may include special slots or a closure. The latest reset or anchor on/before a date determines rotation; dates before the earliest anchor are calculated backwards.
- Precedence is school rotation, school exception, personal cycle override, personal date override. Cycle overrides preserve school closures. A personal date override may reopen a date. Personal changes do not advance the shared rotation.
- Schedule selection: the student's private custom schedule, else the school's variant for the student's grade (`gradeSchedules`, via `scheduleForGrade`), else the school default. Overrides apply on top of the selected schedule.
- All dates use the school's IANA time zone. Repeated fall DST times use the earlier occurrence; nonexistent spring times are reported and skipped. Impossible/cross-midnight shifted slots are retained in storage and reported as issues, rather than causing the app to crash.
- Current period is shown until its end alongside the next future period, including lunch and unassigned periods. Search is bounded to 370 days by default; empty calendars return no upcoming period.

Schedule and personal objects use strict validation, stable IDs and real dates. They are edited through structured editors built on the same schemas (`ScheduleEditor`, `SlotsEditor` and `ExceptionForm` in `schedule-editor.tsx`, plus `ScheduleGrid` and `ClassAssignmentGrid`); no screen edits the raw JSON. Changing a school's period or cycle ID is a semantic change, not a rename.

## Offline queue and conflict handling

Entities are either tasks (one per ID) or the `personal` document (classes, assignments, overrides, optional custom schedule). Versioned tombstones preserve deletion information. The API returns a full account snapshot including tombstones. IndexedDB persists the account's baseline, optimistic local entities, queue, conflicts, cached workspace metadata and retry state. Reloading does not remove pending edits. Local storage failure is reported before an edit is treated as saved. Each signed-in load only reads whether the browser already keeps this origin's storage (`storagePersistence` calls `navigator.storage.persisted()`, which never prompts). The first change saved on a page then asks the browser to keep it (`requestPersistentStorage` calls `navigator.storage.persist()`, at most once per page), because the queue is the only copy of unsynced edits. The request waits for a save because Firefox shows a permission prompt for it. Browsers grant that by their own heuristics; when one refuses, storage stays best-effort and can be evicted under storage pressure, and the Account sheet says so ("Device storage").

Every queued operation has a random mutation ID, a base entity revision and the intended data or deletion. Once first attempted, the wire payload stays fixed until a reply is processed. Server receipts make lost responses and retries idempotent. Reusing an ID with different data is rejected. Server history validates the supplied base revision. Unsent changes following an earlier local edit are rebased onto its acknowledged server entity. A task's `imported` calendar metadata is server-owned: every payload carries its base's value, so a draft or undo snapshot taken before a calendar refresh never reads as an edit to it. A task's `completedAt` is server-owned too: the device stamps it optimistically when it saves a completion, but a payload's value never counts as an edit in a merge, so two devices completing the same task never conflict over it. The server stamps it only when a sync turns `completed` on (keeping the device's stamp unless it is missing or in the future, so offline completions keep their time), carries it while the task stays completed and drops it on reopening or in the next repeat. Bundles built before `completedAt` parse tasks strictly, so current clients send `clientVersion` (`TASK_CLIENT_VERSION` in `src/domain/task.ts`) with `workspace` and `sync`. A request without it (a tab left open across the deploy, or one started offline from the cached shell) gets tasks without `completedAt`, while the stored data and receipts keep it. Old and new tabs share the device store, so a base revision that differs from the recorded one only by a missing `completedAt` is accepted from any client and merged against the recorded revision. Raise `TASK_CLIENT_VERSION` whenever task data gains a field an older bundle would reject. If the server refuses a payload outright (a validation `BAD_REQUEST` or a `CONFLICT`), resending it unchanged would fail forever, so it is parked as a choice for that entity alone, with the server's reason: the student tries it again on top of the saved version or discards it, and uploads for every other entity continue.

Three-way merging applies independent field changes. Collections with stable identities can merge changes to distinct entries. Competing edits to a field, edit/delete races and incompatible ordering become explicit conflicts. Merges that violate model invariants also become conflicts (for example, one device deletes a class while another assigns it). The local intent, base and server value are retained until the student chooses. Keeping the local changes takes the local value only at the competing paths and keeps the other side's independent edits; when that combination would break an invariant, the whole local version is kept. A resolution sends a new operation against the current revision and can conflict again if another device changes it first. Conflict receipts preserve repeatability; they never overwrite server data.

School schedule corrections are independent of personal records. Membership stores the last reviewed school revision; a member who publishes a revision while up to date is marked as having reviewed it, so they are not asked to review their own edit. Workspace snapshots include the old and current default until review acknowledgment. The shared domain helper flags removed period/day targets and shared changes under personal overrides; acknowledgment preserves all personal overrides. Fable can present the same retained values with more focused editing controls.

Service-worker cache contains only the public shell and static assets. Account changes are verified before uploads and the server binds each upload to the expected account. Signout requires connectivity and clears local account data (the IndexedDB record, and the account's `quasar-push:<id>` and `quasar.setup.*.<id>` localStorage keys) only after server logout succeeds and pending changes have been saved or explicitly discarded. In-memory chat drafts and unsent messages are forgotten only once sign-out has finished; a sign-out that fails keeps them. The signing-out tab first sets a sign-out marker on the account's IndexedDB record (`beginSignOut`, expiring after two minutes), and every other tab of that account refuses to queue, resolve or upload changes while it is set, so a discarded change is not uploaded elsewhere. The signing-out tab always releases its own marker when it finishes, even if the final sync ended in a sign-in prompt that closed its store (`endSignOut` then clears it through a fresh connection, and only while that tab still owns it). A new sign-in on the same device is therefore not blocked as "Signing out in another tab". A sign-out that keeps changes re-checks the queue in the same transaction as the delete (`clearOfflineAccount(..., { requireEmptyQueue: true })`) and keeps the cache if a change arrived meanwhile. Sign-out is refused ("Your session changed") when the cookie's account is not the one the tab shows, because `signOut()` would end that other account while clearing this one's cache. No OAuth credentials or tokens are stored in IndexedDB.

## Operational limits

This is a single-server SQLite implementation. History and receipts are intentionally retained so a long-offline device cannot lose its merge base; monitor disk growth and design a device-aware retention policy before pruning. Instead, sync bounds what one account can add: at most 5,000 live tasks of the student's own, counting completed ones (a new task past that is refused with a reason, while edits and deletions still go through). Calendar imports that still carry their `imported` metadata do not count, since the feed limits bound them; tasks detached by removing a feed do count. Per rolling day the limit is also 5,000 applied changes or about 100 MB of synced data (measured in bytes: the sum of the day's stored receipt sizes via `octet_length`, which does not read the receipt text) (`TOO_MANY_REQUESTS`; the device keeps the changes and retries later; replays of an already-applied change always answer). A school schedule is capped at 256,000 characters of JSON on create, edit and proposal. School search (`school.list`, input `{ query, summaries: true }`) returns up to 100 summaries without schedules; the picked school's schedule comes from `school.get`. A call without `summaries` comes from an older bundle that reads `schedule` from each result, so it gets the reload message (`OUTDATED_CLIENT_MESSAGE`) instead of results it would crash on. Full workspace snapshots suit the pilot; pagination/delta sync are future scaling work. There is no capacity claim before load testing. See the operations checklist for backups, monitoring and migration triggers.

## Lunch menu

A school can follow one menu on a Nutrislice site (`schools.menu_source`, JSON: organisation, domain, school page and menu-type slugs, plus the site's own label; see `src/domain/menu.ts`). Supported domains are `nutrislice.com` and the FLIK white label `flikisdining.com`; the org and slugs are validated as lowercase slugs, so every fetched address is `https://{org}.api.{domain}/menu/api/…` and never a private host, and redirects are refused. The owner may set or clear it for any school; a member may while the shared schedule is open to member edits (the `Service.updateSchool` rule); a locked school's members send a correction request. Setting a menu re-reads the site's `/menu/api/schools/` listing and stores the label from there, never client text. `school.menu({ date })` returns the provider week (Sunday to Saturday) containing the date for the caller's school, parsed to per-day notes (holiday names) and station sections with food names only (no nutrition, prices or images). Weeks are cached per school in `menu_weeks` for `MENU_CACHE_MS` (three hours) and served stale, flagged, when a refresh fails; rows older than 60 days are pruned on each write, and changing the source drops the school's rows. Lookups and changes each fetch from the provider, so they share a limit of 30 per account and hour counted in `audit_log` (`menu.lookup`, `school.menu`). Fetches wait at most 10 s and read at most 2 MB. The client keeps a loaded week in memory for 10 minutes, shared by Today, Schedule and School; the menu is never stored on the device.

## Phase 2: calendar feeds, repeat tasks and reminders

Calendar subscriptions belong to one account. The server encrypts private feed URLs with AES-256-GCM using a key derived from `NEXTAUTH_SECRET`; listings and errors never return URLs. Back up that secret with the database. If `NEXTAUTH_SECRET` is missing or shorter than 32 characters, no feed can be read. The worker's calendar step refreshes nothing and logs a `PRECONDITION_FAILED` error each cycle. A manual Refresh reports "Calendar encryption is not configured." Feeds keep their stored state instead of showing the "encryption key changed" error. Each row also stores a `url_hash` that finds the account's existing subscription when the same link is added again: `k1:` followed by an HMAC-SHA-256 of the owner ID and normalized URL under a second key derived from `NEXTAUTH_SECRET`, so a database reader can neither test a guessed or leaked feed URL against the rows nor tell which accounts share a feed. Rows saved before keyed hashes hold an unkeyed `sha256(url)` without the prefix; the web server rekeys an account's rows whose URL the current secret can decrypt when that account loads its workspace (`rekeyOnLoad`), and adding the same link finds and rekeys such a row too. The worker never rekeys: it runs from source, so a restart between a source update and the web rebuild would otherwise rewrite hashes that the still-serving old bundle can only find unkeyed, and re-adding a linked calendar there would duplicate it. If the secret changes, each feed fails with an "encryption key changed" error until its owner adds the same calendar link again, which re-encrypts the stored URL, stores the new keyed hash and refreshes the feed in place with its existing tasks (removing and re-adding the feed instead would import every item again as a new task next to the detached copies). A row that still holds an unkeyed hash is found by that hash. A keyed hash made with the old secret cannot match the link, so while the owner has such unreadable rows, adding any link first fetches it once as a probe and reconnects it only to the one old feed it clearly is: most of that feed's in-window items (not counting ones already marked removed) must be in the fetched feed, and most of the fetched UIDs among the old feed's, because different feeds often share UIDs (an event invited onto two calendars, an "all events" feed over a "sports" one). If no old feed qualifies, or more than one does, the link becomes a new feed. So reconnecting has limits. The probe counts as a `calendar.add` (the new feed it may become is not counted again), so a student at the hourly or daily limit below gets `TOO_MANY_REQUESTS` even when re-adding their own feed. An old feed with no stored calendar items (an empty feed, or one whose first fetch failed), or a probe fetch that fails, cannot be matched: re-adding the link creates a second subscription and leaves the broken one behind, and every later addition by that owner costs an extra probe fetch until the stale feed is removed. Fetching permits only public HTTPS hosts on port 443, validates every DNS answer and redirect, pins the approved destination, and limits time and body size. Each account can hold at most 10 feeds and add at most 20 new ones per hour and 40 per day; additions are counted in `audit_log` (`calendar.add`), so removing feeds never refunds them, because every new feed is fetched immediately. The saved feed content is private database data, just like imported tasks.

The worker checks due subscriptions every minute and refreshes successful feeds every 30 minutes. Each cycle refreshes due feeds oldest first, five at a time, and stops starting new fetches after 20 seconds so the reminders later in the same cycle are not held up; feeds left over stay due and go first in the next cycle. A feed removed while the worker's batch is running is skipped without stopping the rest of the batch. The Refresh button fetches a feed at most once a minute (adding a feed counts as a fetch), so a school server is never hammered; a click inside that minute, or while another refresh is still running, is refused with a `TOO_MANY_REQUESTS` message that says so instead of silently doing nothing. Failures back off from five minutes to six hours without changing saved items. A conditional HTTP 304 still expands cached calendar content so the rolling window advances. Parsing covers the previous 90 days and next 365 days in the chosen calendar time zone. An item is kept when its span from start to due date overlaps that window, so a VTODO that started earlier but is due inside it is imported and tracked; an event is due on its start date, so it is filtered on that alone. Unsupported subdaily recurrence (FREQ=HOURLY, MINUTELY or SECONDLY, or BYHOUR, BYMINUTE and BYSECOND lists that together name more than 24 times a day, which fails with "Calendar recurrence is too complex."; a few times a day, such as a class that meets at 8:00 and 14:00 on Mondays, imports as separate occurrences), RANGE overrides, period-valued RDATE, malformed calendars and compressed responses fail the refresh as a whole, as do feeds over 2 MB, more than 2,000 VEVENT/VTODO entries, or more than 2,000 occurrences inside the window. The stored error names the reason only when it is one of the fixed, URL-free messages from `feed-fetch.ts` and `ical.ts` (for example an HTTP status or one of these limits); anything else gets a generic message, because raw exceptions can quote the private URL. DNS outcomes get the generic message too. The refusal for a host that resolves to a private or CGNAT address is never shown, because it would tell a student which internal or tailnet host names the server can resolve. A single item the task schema cannot hold (titles are trimmed, whitespace-only titles become "Untitled calendar item", and links longer than 2,000 characters after normalization are dropped) is skipped and retried on the next refresh rather than failing the feed. A VTODO with neither DTSTART nor DUE (both optional in RFC 5545) has no date to land on and is left out; a VEVENT without DTSTART still fails the refresh.

Each imported task is identified by subscription, UID and recurrence ID. A RECURRENCE-ID matches its master occurrence by instant, so an override written in UTC or another zone still replaces the occurrence and keeps that occurrence's identity. Imports made before this stored such an override under its own RECURRENCE-ID text, next to a duplicate task for the original occurrence. The first refresh moves the override's task, with its completion and edits, to the occurrence's identity and marks the duplicate as removed from the source. If the student had deleted the override's task, it is left deleted. Repeated refreshes preserve completion and personal fields. Source-only changes update title, notes and deadline; competing local changes create a choice in Connected calendars. The choice is checked against the task's version and the conflict's own revision, so if a refresh changes the source values or adds fields after the choice was shown, the student is asked to review it again instead of accepting values they never saw. The due date and time merge as one value (a choice that covers either applies both), and when a source date or time would leave the task invalid (for example a new time on a task whose date was cleared), only the due date and time become a choice. Other source-only changes in the same refresh, such as a new title, still apply, so one task can never stop the rest of a feed from refreshing. Missing or cancelled occurrences within the active window remain visible with a removed-source label. User-deleted tasks remain deleted. Removing a subscription detaches its surviving tasks instead of deleting them. Imported calendar placement follows source times even when a personal deadline differs.

Completing a manually recurring task creates its next occurrence inside the same transaction as the sync receipt. A permanent parent/successor record prevents duplication after retries, reopening or deleting a successor. Daily, weekly and monthly repeats preserve their original monthly anchor through short months. Task dates share the schedule's 1900–2199 range; a series whose next date would fall past 2199 ends instead of storing a successor the schema rejects. Older builds accepted any 4-digit year, so migrations 11 and 13 repair stored tasks whose due, repeat-end, monthly-anchor or calendar-import start/end date is outside that range (`repairTaskDates`: the date is dropped; a dropped due date also clears the due time, reminder and repeat that need it, a dropped import end date also clears its end time, and an out-of-range import start date drops the calendar link, which the next refresh restores) as a new entity version, and the client's `taskItems` applies the same repair to a cached copy, so such a task stays visible and editable instead of being hidden. Migration 13 re-runs the repair for databases that recorded migration 11 before it covered import end dates. The iCalendar parser likewise leaves off an event end after 2199, so an event running past it still imports. Offline completion creates its successor when synchronized.

Browser reminders require explicit enrollment per browser. Mutations bind to the original account, and sign-out removes the browser subscription. An account keeps at most 10 enrolled browsers (`PUSH_SUBSCRIPTION_LIMIT`): enabling another drops that account's oldest other browser, and enrollment refuses an encryption key that is not a valid P-256 point. A stored browser that no longer passes those checks is deleted on its next delivery attempt, like a 404/410. `deliverDue` reads tasks first and loads an owner's browsers only for reminders that are due; an SQL prefilter (`REMINDER_CANDIDATES_SQL`) passes only live, uncompleted tasks with a reminder and a due date from 3 days back to 9 days ahead to the task schema, and reminder delivery rows more than 2 days past their instant are deleted after each run. Notifications contain generic text, never task titles. VAPID values that web-push would reject (a subject that is not an `https:` or `mailto:` URL, wrong key lengths) or a public key that does not belong to the private key count as not configured: push stays disabled and the server logs one fixed line without the values. The worker logs each push step's non-zero failed count, never provider text. The worker uses durable delivery records, a five-minute retry lease and at most five attempts, removes expired endpoints, and ignores completed/deleted/source-removed tasks and reminders over 24 hours late. The 24-hour window only tolerates lateness: a browser never receives a reminder that came due before it was enrolled, so re-enabling (Disable, sign-out or a key change deletes its delivery records) or adding a browser does not replay earlier reminders. A browser removed partway through a run is skipped without stopping the other deliveries. Delivery is best effort; a crash after provider acceptance can retry the same notification, whose stable tag collapses visible duplicates. Date-only reminders use 09:00 in the saved reminder time zone; DST gaps move forward and folds use the first occurrence.

## Phase 3: verification, community and voting

Schema migration 4 adds `school_verifications`, `verification_requests`, `friendships`, `blocks`, `reports`, `school_bans`, `schedule_proposals`, `proposal_votes` and `schools.email_domains`. Rules live in `src/server/community.ts` and `src/server/proposals.ts`; every server read re-derives access from the current rows, so there is no cached permission to invalidate on the server. The workspace `classmates` list is held only in the viewer's app memory, never in the device store, so an already open app shows a former friend only until its next successful sync (see the workspace bullet below).

- Verification is keyed by (user, school). `join` verifies automatically when the account's email domain matches one of the school's domains (exact or subdomain), and so does `verification()` (called for every workspace load) for a current member when support adds a matching domain after they joined. A domain verification also closes that student's open proof request as approved (actor NULL), so it leaves the admin queue, and `school.adminUpdate` audit rows record `fromDomains`/`toDomains` whenever support changes the domain list. Otherwise students send a proof text that the owner approves or declines in the admin page. Three declines in a week block further requests.
- Friendships are stored once per unordered pair (`user_low`, `user_high`) with the requester and a `pending`/`accepted` status. A profile returns the friend's classes and personal schedule document only when the pair is `accepted`; the client renders the friend's day with the shared domain resolver. Requests require the same school and neither side blocking, and accepting one re-checks both (a pending request whose two people no longer share a school is deleted with `NOT_FOUND` instead of accepted); accepted friendships persist across school changes but never reveal more than the friendship allows.
- Blocks are directional rows; either direction hides both members from each other's directory and profile, except that the blocker can still open the blocked profile to lift the block. Reports and support removal (`school_bans`) are owner-reviewed; a ban clears the student's school and verification at that school, declines their open verification request there (and approving a request for a banned student declines it instead), ends every friendship they have at any school (closing all their chats, [CHAT.md](CHAT.md) D4) and rejects future joins to that school.
- Proposals store the full school schedule (all grades) at a base revision. Votes are upserted per member; the tally runs inside the same transaction and applies a passing proposal as a new `school_revisions` row and sets `schools.approved=0` (an owner publishing an awaiting-support proposal keeps the approval), or parks it as `awaiting-support` when the school is support-locked. Any revision change supersedes open and awaiting-support proposals: an owner or member school save closes them in the same transaction, and the owner's awaiting-support list and publish action first close any that a newer revision has overtaken, so a stale proposal is never offered for publishing. Thresholds derive from the count of verified members at tally time, and while a proposal is open its for/against counts include only votes from people who are still verified members of the school, so a vote stops counting when its voter leaves, switches schools, is removed or loses verification. Each tally stores those counts on the proposal (`tally_for`, `tally_against`, migration 12), and a closed proposal shows its last tally, so a recorded result never changes after the fact. Proposals closed before migration 12 show their raw vote counts. Those same events withdraw the member's own open proposal there.
- Workspace payloads include a `community` summary: verification status, incoming request count and friend count for badges, the chat badge fields (`unreadChats`, `unreadAt`, `chatPush`, see [CHAT.md](CHAT.md)), and `classmates`, each accepted friend at the viewer's current school with their id, display name and class names per period (from `CommunityService.classmates`), which the Today and Schedule timelines use to say who shares a class. Friends at another school are left out (friendships survive a school change, but period ids such as `p1` or `A` repeat across schools), and the profile's "Together" chips likewise only compare classes when both people are at the same school. `classmates` is held in memory only: the copy of the workspace context saved in the account's IndexedDB store has an empty list (`persistedContext` in `src/components/app-state.ts`), so friends' names and timetables never sit on the device's disk, and an offline start shows no "With …" tags until the first successful sync. The saved context is stamped with `CONTEXT_VERSION` (`storedContext`), and `cachedContext` ignores a copy stamped by another version, so a context saved by an older build is never rendered as the current shape (the network load replaces it; offline, the device shows "Connect to get started" until it has been online once). An unstamped copy saved by the build just before `CONTEXT_VERSION` existed has the version-2 shape: when it has `user.suggestedNames` it is read as version 2 with its `classmates` dropped, and the next attach re-saves it stamped in one transaction (`upgradedContext`, `OfflineWorkspace.upgradeContext`), which also removes the friends' data that build wrote to disk. Unstamped copies without `suggestedNames` (older builds) are still ignored. Bump `CONTEXT_VERSION` whenever the workspace context gains, loses or changes a field the client reads. The server recomputes the list on every workspace load, so an unfriend, block or support removal drops the former friend on the viewer's next sync. Directory and proposal lists are fetched on demand and are never cached by the service worker.

## Phase 4: chat

The full spec is [CHAT.md](CHAT.md). Schema migration 6 adds `chat_threads` (one row per unordered pair, with a revision counter and `last_message_at`), `chat_members` (per-person read marker, push marker, mute and first-send time), `chat_messages` (a global `seq`, a client ID unique per sender, the revision at insert or last delete) and `chat_pauses`. It also adds `thread_id`, `evidence` and `category` to `reports` and `chat_push` to `users`. Rules live in `src/server/chat.ts`; constants live in the `CHAT` object in `src/domain/chat.ts`. Migration 7 adds the public Global chat room (`global_chat`, `global_messages`, `global_members`), whose rules live in `src/server/global-chat.ts` and [CHAT.md §11](CHAT.md#11-global-chat-migration-7). The bullets below describe one-to-one chat unless they name the room.

- **Access is re-derived on every call.** `access(viewer, other)` requires both names, an accepted friendship and no block in either direction, checked inside the same transaction as the read or write. Nothing is cached, so an unfriend, block or support removal closes the chat on the very next call. A chat that fails access returns "This chat is closed." whatever the cause. `chat_members` is state, never a grant. Reporting needs only `member` (a thread row for the pair), so a student who was blocked or unfriended can still report: the closed row shows in the chat list for 30 days (`CHAT.closedRowDays`), and a report stays possible (for example from the People profile while it is still visible) until retention deletes the thread, 180 days after the last message.
- **Global chat is one public room across schools.** Any account with both names entered can read and post in it, with no school, friendship or verification check (`GlobalChatService` only calls `service.ready`). The room has no Block, Report or closed state of its own; a member can mute it. A block made elsewhere (a profile or a one-to-one chat) applies one way: the blocker no longer sees the blocked member's room messages in the thread, list preview, unread count or pushes (`NOT_BLOCKED_SENDER_SQL`), and the blocked member's view does not change. Messaging pauses and the per-minute and per-day send limits apply, and slurs are censored before storing in both kinds of chat (`src/domain/chat-filter.ts`; `censorBody` keeps `https://` links whole so they still work, and bubbles hide a slur inside a link at display time). The owner moderates it directly: `global.edit` (`adminScoped`) edits any message and `global.delete` removes anyone's message when the owner calls it (a sender can delete only their own), each with a reason everyone sees and an `audit_log` row (`global.edit`, `global.delete`).
- **Every chat procedure is `accountScoped`, queries included**, so a tab left on one account can never read another account's chats after a switch. The four admin chat mutations use `adminScoped` (owner check on top of `accountScoped`), so an evidence view is never logged under the wrong account.
- **Sends** run self check, body normalization, access, the idempotency lookup on `(sender_id, clientId)`, the pause check, then the rate limits, in one transaction. A retry returns the stored message and never uses up quota. Body errors are fixed strings, never the message text, and tRPC errors are logged through `logTrpcError` in `src/server/trpc-log.ts`.
- **Polling, not streaming.** The client polls `chat.thread({ after: revision })` every 4 s for an open thread and `chat.inbox` every 10 s for the list, only while visible and online, with backoff to 30 s. The revision cursor returns new, deleted and hidden messages; more than 200 changes or a cursor ahead of the thread returns `reset: true` with the latest page. `chat.send` returns no revision, so the client only advances its cursor from polls and cannot skip the other person's messages. `chat.send` and `scan.schedule` go through their own `httpLink`; everything else stays on `httpBatchLink`. Every request times out on the client (30 s, 120 s for a scan), so a stalled connection cannot freeze sync or polling. The unread badge uses server-stamped `unreadAt`, newest wins.
- **Push.** The worker cycle runs `refreshDue`, `deliverDue`, `deliverChat`, `deliverSupport` and the chat prune step (`pruneChat`, then `pruneGlobalChat`) in order. `deliverChat` sends a fixed payload `{"kind":"chat","tag":"quasar-chat"}` with no names or text, only for unmuted messages still unread 60 s after they arrive (the Global chat room is one more candidate, `GLOBAL_CANDIDATE_SQL`, for every account with names and `chat_push` on, the default, that has not muted the room), at most one per recipient per 10 minutes and 20 per day, never from 22:00 to 07:00 in the school's time zone (fallback `America/New_York`), and never when `chat_push` is off. It claims `notification_deliveries` rows with `entity_id='chat:messages'`, rechecks access and read state before sending, and records `notified_seq` so a restart does not push the same messages again. `deliverSupport` pushes the owner's enrolled browsers (the `OWNER_EMAIL` account) a generic notice, the fixed payload `{"kind":"support","tag":"quasar-support","url":"/admin"}`, once per browser for each new unresolved support request, verification request, report or proposal awaiting support from the last 24 hours that arrived after that browser was enrolled, claiming one `notification_deliveries` row per item with `entity_id='support:<table>:<id>'` (deleted after 7 days) and rechecking the item is still open before sending.
- **Retention.** `pruneChat` runs every cycle: messages are deleted 180 days after they are sent, deleted messages lose their text after 30 days, report evidence is cleared 180 days after the report is resolved, threads with no message in 180 days are deleted with their members, and chat delivery rows go after 2 days. `pruneGlobalChat` runs in the same step: room messages are deleted 180 days after they are sent and deleted room messages lose their text after 30 days.
- **Nothing on the device.** Messages, drafts and unsent messages live in a module map in `use-chat.ts` for the open tab and are cleared when the account changes. They never enter IndexedDB, the offline queue, localStorage or the service-worker cache. The cached workspace holds only `unreadChats`, `unreadAt` and `chatPush`.
- **What the owner can see in one-to-one chat.** Only report snapshots. A chat report freezes up to 30 messages from that one chat into `reports.evidence`. The owner sees them only by pressing Show messages, which is the `admin.showEvidence` mutation and writes a `reports.view` row to `audit_log`. Hide message, pauses and lifted pauses are audited too. No admin procedure reads `chat_messages.body`, lists anyone's chats, or shows who talks to whom or read state; a test pins the exact admin procedure list. Support has no chat account. The Global chat room is the deliberate exception: the owner reads `global_messages` in the app like any member and can edit or remove any of them.
- **Not encrypted at rest.** Messages and report evidence are stored as plain text in SQLite and in its backups. The guarantee is that no product or API path shows unreported chats and that evidence views are audited; see the operations rule on chat data.
